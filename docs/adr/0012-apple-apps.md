# ADR-0012: Apple apps (iPhone, iPad, Mac) in SwiftUI

- **Status:** Accepted
- **Date:** 2026-10-15
- **Supersedes:** [ADR-0008](0008-ui-framework-strategy.md)
- **Related:** ADR-0003, ADR-0004, ADR-0007, ADR-0009, ADR-0014, [`../protocol/discovery.md`](../protocol/discovery.md), [`../protocol/threat-model.md`](../protocol/threat-model.md)

## Context

- ADR-0008 chose native mobile UIs. For the desktop it provisionally picked Tauri 2, gated on a spike that was never run. Milestone 2 needs an app the maintainers can install on an iPhone, an iPad and a Mac.
- The core is reached through `dropumi-ffi` and its generated Swift bindings (ADR-0009).
- The identity stays a key file in app-private storage (ADR-0014).
- The plan for this milestone set out the remaining choices: D1 (Share Extension), D3 (receive folders), D4 (discovery), D5 (background), D9 (honest labels), D10 (sending to a listed device) and D11 (interop tests).

## Decision

**One SwiftUI codebase for iPhone, iPad and Mac** (`apps/apple`). It supersedes ADR-0008's provisional desktop choice for macOS. Windows and Linux stay undecided, under ADR-0008's gates (G1 integration feasibility, G2 measured budgets).

| Target | What it is |
|---|---|
| `Dropumi-iOS` | iPhone and iPad (iOS/iPadOS 27.0), arm64 |
| `Dropumi-iOS-ShareExtension` | The share sheet entry. It never links the Rust core. |
| `Dropumi-macOS` | Mac (macOS 27.0, arm64), sandboxed, hardened runtime with no exceptions, plus a menu-bar receiver |

- The Xcode project is generated by xcodegen 2.46.0 from `apps/apple/project.yml` and is not committed.
- Swift 6, strict concurrency. The app's code is main-actor by default; the package modules are not.
- **Layers** (local Swift package `DropumiKit`):
  - `DropumiCore`: paths, Bonjour, the core client;
  - `DropumiAppState`: an `@Observable` `AppModel` that holds all state and reduces the core's events;
  - `DropumiDesign`: design.md tokens, Plus Jakarta Sans under the OFL, components;
  - `DropumiShare`: the share inbox.
- The screens only render `AppModel`. Every core call runs off the main thread.
- **Consent rules in the UI:**
  - **No automatic answers.** The app never answers a prompt by itself. A prompt disappears only when the core closes it. At zero it reads "Expired".
  - **Hardened buttons.** There is no default button. Escape declines. Accept and "Codes match" are enabled 600 ms after the prompt appears.
  - **No auto-trust.** Accepting an offer never trusts the sender.
  - **Labels.** A nearby device whose hint matches a paired one reads "Looks like ‹alias›", never "Paired". An unverified peer is "Unverified device" with the name it claims.
  - **Literal peer strings.** Peer strings are rendered literally (`Text(verbatim:)`).
- **Share Extension (D1).**
  - It copies shared items into `inbox/.staging-<id>/` in the App Group `group.io.github.dropumi`, writes a manifest of names and sizes, and renames the folder into place in one step.
  - The app checks every batch against its manifest and opens Send with the files.
  - iOS has no public way for an extension to open its app, so the extension says "Open Dropumi to choose a device".
- **Storage (D2, D3, ADR-0014).**
  - **Identity.** `Application Support/Dropumi` in the app container. The core creates it 0700; the app sets `isExcludedFromBackup` on both platforms, plus `completeUntilFirstUserAuthentication` on iOS.
  - **Received files.**
    - iOS: `Documents/Received`, visible in Files.
    - Mac: `~/Downloads/Dropumi`, or a folder the user chooses, kept as a security-scoped bookmark. Files are received with `LSFileQuarantineEnabled`.
- **Discovery (D4).**
  - The Bonjour adapter registers a proxy: A records for a random host plus the service on that host. The SRV target is therefore never the system's host name (gate G2, `discovery.md` §3, §7).
  - Registration does not wait for DNS-SD's answer. Until the user answers the Local Network question, DNS-SD does not answer, and waiting held up the receiver and dropped the advertisement.
  - Browsing runs only while a device list is visible.
- **Background (D5).**
  - **iPhone and iPad** receive only while Dropumi is open. In the background the receiver stops accepting and running transfers may finish. A transfer the user started asks for `BGContinuedProcessingTask` time; if iOS ends that time, the transfer is cancelled cleanly.
  - **Mac.** Closing the window keeps the menu-bar receiver running (the Dock icon goes away). "Quit Dropumi completely" stops receiving and withdraws the advertisement. "Open at login" uses `SMAppService` and is off by default. Notifications are asked for in context; an offer notification has no Accept action.
- **Tests (D11).**
  - Tests use temporary folders and their own settings (DEBUG only), never the real identity.
  - UI state tests run the app on a fake core, compiled into Debug builds only.
  - An opt-in harness drives the app's real core inside an app-hosted XCTest against the real CLI.
- **Build checks.**
  - The XCFramework is stamped with a hash of the Rust sources it was built from; Xcode refuses a stale one and never runs cargo itself.
  - Signing is automatic. The team ID comes only from a gitignored `Signing.local.xcconfig`.

## Spike results (2026-10-15, macOS 27.0.1 arm64, Xcode 27.0, local runs)

| ID | Question | Result |
|---|---|---|
| S-A1 | Can a harness drive an app-hosted XCTest and read its status live? | **Yes**, on the iOS 27.0 simulator and on macOS. `xcodebuild test-without-building` with `TEST_RUNNER_DROPUMI_*` variables; the test's `DROPUMI_STATUS {json}` lines stream on xcodebuild's output while the test runs. |
| S-A2 | Bonjour: random SRV host, both directions | **Partial.** Proxy registration works from an unsandboxed process on the Mac and from a test process in the simulator (probe registered `dropumi-probe001`); `dns-sd -P` showed a plain registration publishes `LocalHostName`. **Inside the app's process on the iOS 27.0 simulator, DNS-SD requests are accepted but never answered** (registration, browse; no prompt shown). The sandboxed Mac app and real devices: not tested. |
| S-A3 | `BGContinuedProcessingTask` with a live transfer | Not tested (needs a device). |
| S-A5 | Does the sandboxed Mac app need Local Network approval for loopback? | **No** for loopback: the interop tests (transfers both ways and pairing on 127.0.0.1) ran without a prompt. |

## Implementation

**Code**
- **App code:** `apps/apple/` contains `project.yml`, `Config/`, `Dropumi/{Shared,iOS,macOS}`, `ShareExtension/`, `Tests/`, `README.md` and `Design/macos-app-icon.svg`.
- **Package modules:** `apps/apple/DropumiKit/Sources/{DropumiCore,DropumiAppState,DropumiDesign,DropumiShare,DropumiTestSupport}`.
- **Scripts:** `scripts/apple/check-core-artifacts.sh`, `scripts/apple/interop.sh`, `scripts/apple/render-mac-icon.sh` and `scripts/ffi/core-sources-hash.sh`.
- **Harness:** `crates/cli/tests/e2e/interop/apple.rs`.

**Tests**
- Package (`swift test`, macOS host): `ShareInboxTests` (8), `BindingsTests` (6), `AppModelTests` (27).
- App-hosted: `TestHostTests` (5) on the iOS 27.0 simulator; `TestHostTests` (3) and `MenuBarReceiverTests` (3) on macOS 27.
- UI state tests (fake core): `UIStateTests` (9) on the iPhone 17 / iOS 27.0 simulator, 4 of them with the accessibility audit. The audit found and we fixed:
  - small accent text below 4.5:1 (the new `accentText` token);
  - fixed-size code digits;
  - small hit areas;
  - text clipped at large sizes.
- Interop (opt-in): `e2e interop::apple::apple_{ios_sim,macos}_{app_sends_to_cli_after_code,cli_sends_to_app_after_code,pairing_codes_match}`, plus `apple_macos_bonjour_*`.

**Status**
- Package, app-hosted and iOS UI state tests: Automated test passed (iOS 27.0 simulator and macOS 27.0.1 arm64, local run).
- Interop with the CLI over loopback: Automated test passed (6 tests: iOS 27.0 simulator and macOS 27, loopback, local run).
- macOS UI state tests: Not tested (UI automation needs the user's approval on the machine).
- Bonjour interop: Not tested.
- Devices (iPhone 15, iPad Air 5, the Mac on a LAN): Not tested (device matrix pending).
- CI job `apple (app)`: Not tested (pending CI; fails loudly without Xcode 27, gate G5).

**Privacy manifests**
- Checked against the symbols a Release build imports (`nm -u`):
  - file-timestamp APIs (`stat`, `fstat`, `lstat`, URL modification dates): C617.1, 3B52.1;
  - `UserDefaults`: CA92.1.
- No disk-space or boot-time API is linked once dead code is stripped.

**Not measured**
- Idle memory and CPU of the Mac app with the window open and closed (ADR-0008's M1 and M5 methods).
- App sizes with a release-profile core.

## Consequences

### Positive

- One UI codebase for three device types. iPad and Mac get the wide layouts from the designs.
- The extension cannot leak or lock the identity; it never loads the core.
- The receiver starts at once even before the Local Network question is answered.
- The interop tests run the same core through the real Swift layer against the CLI. They catch bridge mistakes that unit tests with a fake core cannot catch.

### Negative

- Bonjour in the app cannot be tested on the simulator; only devices (and the Mac with someone present) can show it working.
- An advertisement that fails after `advertise` returned is removed silently. The UI shows discovery problems only from browsing.
- On iPhone and iPad, receiving needs Dropumi to be open.
- macOS 26 and later may reshape icons that do not follow the new icon format. The Mac icon follows the classic grid and is listed for design review.
- Developer ID notarization, Keychain storage, and Mac share or Services integrations are not done (later milestones).

## Alternatives considered

- **Tauri 2 on the Mac (ADR-0008's provisional pick):** a second UI stack and a WebView for one platform. SwiftUI on the Mac shares the iPhone and iPad code and gets native menu-bar, notification and sandbox integration.
- **Mac Catalyst:** iPad behaviour on the Mac; a menu-bar receiver and Mac window conventions are harder.
- **Network framework (`NWListener` service, `NWBrowser`) for discovery:** cannot set the SRV host, so it would publish the system host name.
- **Waiting for the registration result:** blocked the receiver for up to 5 s and dropped the advertisement on first launch.
- **Running the core in the Share Extension:** memory limits, and a lock held in the shared container can get a suspended process killed; the extension would also need the identity.
